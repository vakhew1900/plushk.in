### SEARCH-8 — Точечная выборка `chrome.bookmarks.get(ids)` вместо полного скана в `BookmarkSearchService`
**Priority:** Low
**Added:** 2026-08-19

`BookmarkSearchService.search()` (`SEARCH-5`, `changelog.md`/`tasks.md`) при любом запросе читает закладки полным сканом `IBookmarkRepository.listAll()` (обход всего дерева `chrome.bookmarks`), даже когда активны фильтры по тегам/категории/статусу и итоговое множество id заведомо маленькое. Оптимизация: сначала сузить кандидатов через уже существующие индексные Dexie-запросы (`getBookmarkIdsByTagIds`/`getBookmarkIdsByEntityType`), затем достать через `chrome.bookmarks.get(ids)` только эти узлы вместо полного `getTree()`.

Сознательно отложено при реализации `SEARCH-5` (см. `specs/tasks/SEARCH-5-bookmark-filters/description.md`) по двум причинам: (1) `chrome.bookmarks.get(ids)` отклоняет весь batch-вызов целиком, если хотя бы один id в массиве не существует (подтверждено по документации Chrome/MDN) — до `BG-1` (каскадная очистка осиротевших связей) это реальный, не гипотетический риск; (2) объём личной библиотеки закладок, скорее всего, не оправдывает усложнение — полный скан уже сегодня используется для текстового поиска без жалоб на производительность, оптимизировать стоит по факту измеренной проблемы, а не заранее.

**Зависит от `BG-1`** — без каскадной очистки осиротевших id в `bookmarkTags`/`bookmarkEntityLinks` батч-запрос `chrome.bookmarks.get(ids)` может упасть целиком на первом же устаревшем id.

На момент постановки не решено: как считать `folderPath` для закладок, полученных точечным `chrome.bookmarks.get(ids)` — сейчас путь строится попутно при обходе всего дерева (`BookmarkRepository.collectBookmarks`), а точечный `get()` отдаёт только сам узел без цепочки родителей; нужен либо отдельный резолвинг пути по `parentId` для каждого найденного id, либо другой механизм — не проработано.

### ARCH-3 — Заменить Map на Record в домене PageMatchGroup
**Priority:** Low
**Added:** 2026-07-24

`PageMatchGroup` (`src/types/page-match.ts`) хранит `pageMatches` как `Map<string, PageMatch>`. Так как `Map` не сериализуется в JSON (данные лежат во внутреннем слоте, не как собственные перечисляемые свойства — `Object.keys(map)` пуст, и `toJSON()` не определён), для каждой границы сериализации завели свой JSON-safe тип с тем же полем как `Record<string, PageMatch>`: `StoredPageMatchGroup` в `db/index.ts` (для Dexie) и `ExportedPageMatchGroup` в `types/settings-export.ts` (для файла экспорта/импорта настроек, см. `SETTINGS-1`). По факту одна и та же форма дублируется в двух местах ради одной и той же проблемы. Рассмотреть замену `Map` на `Record` прямо в домене `PageMatchGroup` — тогда `StoredPageMatchGroup` и `ExportedPageMatchGroup` можно убрать целиком, используя один тип везде.

Риски/нерешённые моменты на момент постановки:
- Это более широкий рефакторинг существующего рабочего кода, а не точечная правка: `Map` активно используется через `.get`/`.set`/`.values()`/`.size` в `src/lib/page-match-mapping.ts` и его тестах, и потенциально в UI вкладки алиасов/переменных (`AliasesSection`/`VariableBlock`) — не проверялись на использование Map-методов.
- `Map` гарантирует порядок вставки независимо от вида ключей; у обычного JS-объекта ключи, похожие на числа, автоматически переставляются в начало при переборе. `page-match-mapping.test.ts` явно проверяет сохранение порядка полей — переход на `Record` нужно делать с сохранением этого инварианта.

### AUDIT-7 — Аудит операций на необходимость Dexie-транзакций (атомарность)

Запрошено пользователем при ревью `SEARCH-6`: `BookmarkQuickSaveLinksRepository.save()` (заведён в той задаче) оборачивает запись `bookmarkTags`+`bookmarkEntityLinks` в `db.transaction('rw', ...)`, по образцу уже существующих `TagRepository.remove()`/`DomainAliasRepository.remove()`/`EntityTypeRepository.remove()` — но это была точечная правка одного метода, а не систематическая проверка всей кодовой базы на похожие пробелы. Аудит касается только последовательностей из нескольких Dexie-записей, не моста между `browser.*` и Dexie — эту границу переписывать не нужно, она принимается как есть.

На момент постановки не решено: считать ли находки этой задачи одним общим PR/коммитом или заводить каждую как отдельный маленький фикс по мере обнаружения; нужен ли явный чеклист/список мест в `specs/tasks/AUDIT-7-.../` (deep spec) прежде чем чинить, или можно чинить по ходу аудита без отдельного интервью.

### UI-13 — Адаптивная вёрстка страницы настроек (options) под сужение окна
**Priority:** Medium
**Added:** 2026-08-16

Поднято пользователем при обсуждении, стоит ли вообще делать адаптив для расширения. Popup имеет фиксированный размер, задаваемый браузером, — адаптив там не нужен. Задача — не полноценный mobile-first адаптив (расширение используется только на десктопе), а базовая гибкость там, где вёрстка может поломаться: `flex-wrap`, `min-width` вместо жёстко заданных px-контейнеров, ориентировочно для окна вплоть до ~900–1000px шириной. На момент постановки не решено: точный список экранов/компонентов, требующих правки — нужен обзор перед стартом реализации.

### NOTE-1 — Заметки, привязанные к закладкам
**Priority:** Medium
**Added:** 2026-08-21

Дать пользователю создавать текстовые заметки и привязывать их к закладкам — свободный пользовательский текст, отдельно от `Tag`/`EntityType` (структурная таксономия, `SEARCH`/`SHELF`) и от `PageMeta.description` (авто-извлекается со страницы, не редактируется пользователем).
